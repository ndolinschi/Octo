## 1. What T3 Code is
T3 Code calls itself an "agent harness control surface": a GUI that drives coding-agent CLIs the user already has installed and signed in to. It uses their subscriptions, not API keys. Supported agents are Codex, Claude Code, Cursor, Grok Build, OpenCode, Antigravity, fx, Kiro, Pi, Muse, plus any agent in the ACP Registry (G/README.md, G/AGENTS.md, G/docs/user/providers-acp.md).
How it is built:
- A Node/Effect WebSocket server (`t3`, apps/server) owns provider processes, terminals, git, files and SQLite. It wraps each provider behind an adapter: Codex app-server, `@anthropic-ai/claude-agent-sdk` for Claude, ACP for registry agents (G/apps/server/package.json, G/docs/internals/providers.md).
- Clients: a React web app (apps/web), served locally by `t3` and hosted at app.t3.codes. An Electron desktop app bundles the server. React Native apps exist for iOS and Android.
- Remote access: LAN, Tailscale, SSH, or the "T3 Connect" tunnel (G/docs/internals/overview.md, G/docs/user/remote-access.md).
- The hosted app is only a client. With no paired computer it shows "No computer connected": Sign in, then `curl … install.sh | sh` and `t3 connect` (live: shots/app.png).
- License is MIT; the site claims 54k+ stars and 500k users; current stable is v0.1.8 (live: t3.codes/download).

## 3. What we have that T3 Code does not
- Project memory notes: titled notes injected into the orchestrator prompt every turn and editable in the UI. T3 has threads plus provider memory only.
- Tiered models per project (fast/balanced/deep) that the orchestrator picks per task. T3 picks one model per thread or sub-agent call.
- Physical isolation: one SQLite file per project; a project can span several folders. In T3 a project is one directory per environment.
- A real code editor: Monaco with LSP plugins (diagnostics, hover, completion, go-to-definition) and line comments sent to the orchestrator. I found no LSP in T3 (grep for language server/lsp in apps/web and apps/server is empty).
- A plugin manifest for language servers, ACP agents and tool servers. T3's providers are built into the code, plus the ACP Registry.
- A dock / tab workspace with side-by-side groups. T3 has a fixed right panel and bottom drawer.
- A model-agnostic harness running behind our own router (Octo autoroute).

## 4. Top 5 by value for effort
1. Turn changes + diff (v7 "Changes"). Small/medium harness work: we already see `write_file` and ACP edit calls. This is the biggest trust gap.
2. Queue/steer during a turn. Small: replace the 409 with a per-project queue; UI shows queued chips.
3. Supervised vs Full access, with ACP permission requests shown in the parent chat. Medium, and it closes "ACP runs unsandboxed".
4. The composer "+" / `@` / `/` menu (decision 10), with effort and image attachments. Mostly UI, small harness work.
5. Lineage/activity panel and "Waiting on N sub-agents · Stop" status line (decisions 15/17 plus the floating-composer chips). UI only, on data we already have.
Next after these: orchestrator compaction, a terminal, worktree isolation per sub-agent.
