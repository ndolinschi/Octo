# UI verification by parts (2026-11-13)

A check, not a fix: no product code was changed. Nine parts of the UI were walked by nine sub-agents (Opus), at most four
at a time, each against the same dev server (`vite` on port 1520, `?demo=1`). The orchestrator then reproduced every
severity A finding itself, merged duplicates and marked what earlier rounds already knew.

**How it was checked.** Chromium through Playwright, demo data, dark and light, at 1440×900, 1100×800, 900×600 and
390×700, device scale factor 1. Each part: screenshots of every state (read by the sub-agent), keyboard and pointer
scenarios, measurements with `getBoundingClientRect`, the browser console. About 1 850 screenshots; they are in the
session scratchpad (`verify/<part>/`), **not in the repository** — paths below are relative to that folder and are
evidence for this pass only.

**What this does not cover.** Demo data checks layout and behaviour, not a live backend. Not verified anywhere in this
pass: macOS and WebKit (the owner's webview), Windows, the Tauri shell, a live harness, real agents, a real `gh`, touch
on a device, a screen reader. Findings that may be the demo bridge's fault rather than the product's say so.

**Severity.** A: a person trips (does not work, covered, clipped, input lost). B: inconsistency or untidiness that makes
a screen look unfinished. C: polish. **Status:** *confirmed* = reproduced by the orchestrator (script re-run or own
script, plus the screenshot read); *reported* = from the sub-agent with steps and a screenshot, not re-run; *known* =
already recorded in an earlier round, the spec's "As built" or `HANDOVER.md`.

## 5. Patterns: one cause, many screens

1. **Focus is not managed after an action** (A1, A9, A11, B1, B29, B57, B59). A control that removes itself, a menu or
   palette that restores focus after the command already moved it, a button that turns `disabled` while pressed, a tool
   tab that opens with focus on whatever is first in the DOM. Fourteen places across seven parts. The fix belongs in
   `primitives/Menu`, `Popover`, `Dialog`, `ListDetail` and the palette, not in each screen. A1 is the costly case:
   returned focus plus single-key approval.
2. **The floating composer is laid over tabs it does not belong to** (A6, A7, B2). It hides content in one-strip mode,
   its chip is transparent, and the hidden conversation composer still answers a global shortcut.
3. **Narrow widths are checked only where a script looks** (A5, A8, A10, A12, A14, B13, B21, B28, B30, B53, B56). Rows
   whose fixed parts (`shrink-0` counts, buttons, chips) do not shrink, and breakpoints written against the window
   where the pane is what is narrow. The side group at 1440 is 363 px, not the ~480 the specs assume. One invalid
   Tailwind class (`max-@3xl:`) removed a whole page; nothing fails on an unknown class.
4. **Popup lists are still several components with several key contracts** (B6, B7, B8, B9): Home/End, Tab, row
   height on touch, following the anchor. Decision 95a/b is met for ArrowDown-after-open and wrap-around only.
5. **Names and words** (A4, B3, B5, B18, B60): model ids where a provider entry is missing, backticks and environment
   variables in prose, protocol words in labels, an error mapping that matches a bare "401".
6. **The panel frame is equal in numbers, not in parts** (B4, B31, B32, B34, B35, B41): empty states, editors' action
   rows, detail header actions and the side question are still each screen's own.
7. **Touch size is not in every primitive** (B8, B22, B47; C at 390: `SearchField` 38, `ViewTabs` 32).
8. **Demo data blocks checking** (B10, B14, B38; C in parts 2 and 4): the queue never drains, "Open file" from
   Changes always fails, no message has a `session_id`, an ACP project has no context categories.
