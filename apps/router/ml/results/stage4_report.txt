Date 2026-11-13. Location: apps/router/ml/. Every number below is in results/stage4_{ladder,workload,controller}.json.
Stages 1-3 code and numbers untouched (git status: only new files plus the Makefile). 33 tests pass (22 earlier + 11 new).

======================================================================================================
L1 - A LADDER THAT LEARNS ITSELF (criterion 2'; make ladder; stage4_ladder.py; figures stage4_regret.png, stage4_adoption.png)
======================================================================================================
Setting, declared before running. 33 arms = one per model of the core slice, the NEWEST submission of each model;
gemini-3.5-flash dropped (no per-instance cost). Per task the policy picks one model and sees only that model's
resolved and cost (Env; test: flipping every cell no stream chose leaves all decisions unchanged, 7 policies).
Streams: 500 Verified tasks, orders random / by repository / by created_at, 200 streams each (created_at: one fixed
order, streams differ only in the policies' randomness). Single runs per cell; regret is realized on the same tasks.
Objective (i): reward = solved - cost / V, V = $ value of one solved task in {inf, $20, $5, $2, $1, $0.5, $0.2}
(cost per task over the arms is $0.03-$1.13, solve rate 0.09-0.77). Objective (ii): min cost s.t. solve rate >=
q x best model's (q = 0.90, 0.95).
Production mirrors. List-price ladder (cheapest low-band / cheapest mid-band / dearest high-band model):
gpt-5-nano / devstral-2512 / claude-opus-4. Leaderboard ladder (best headline per band): minimax-m2.5 /
gemini-3-flash / claude-opus-4.5. Leaderboard $/solved ladder (the production config's own rule, "DeepSWE $/score"):
deepseek-v3.2-reasoner / glm-4.6 / gpt-5. For (i) each ladder is credited with its best rung AT that V in hindsight
(generous). CAVEAT: the headline is the mean of the same 500 outcomes, so the leaderboard ladder is in-sample
here; an out-of-sample version is in L1e.

L1 verdict. Against the production-style list-price ladder, a bandit over concrete models is much better at every V
except quality-only. At V=$1: 0.550 [0.469, 0.602] vs 0.310 reward per task; at the same solve rate as the dearest
rung, cost per solved is $0.54-0.61 vs $1.67. Against any leaderboard-informed ladder it loses: in-sample, and also
out-of-sample from a held-out half (0.497-0.581 vs 0.686 at V=$1), and within 500 tasks it never gets within 0.02 per
task of the best model. Its demonstrated value is adaptation: it adopts a new best model in a median 35-50 tasks and
drops a degraded one in 16-55. Not verified: traffic where the public leaderboard ranks models differently from the
router's own workload (the only case in which L1 should beat a leaderboard on stationary data); this dataset cannot
show it.

======================================================================================================
L3 - THE QUALITY CONTROLLER (criterion 4'; make controller; stage4_controller.py; figure stage4_controller.png)
======================================================================================================
Setting: per stream a random half A of tasks = offline data with full information; half B (250 tasks) = the stream
with bandit feedback. "tiers" = stage 2's setting (3 scheme-A tiers, 0/1 draws from the soft labels, quality scored on
the soft label, reference always-high, tau = 0.95). "models" = L1's 33 arms (reference = best model on half A, tau =
0.95 and 0.90). Honest offline baseline: the cheapest two-arm mixture reaching (tau + d) x reference on half A,
d in {-0.02 ... +0.08}. Controller lcb(conf): before every task, the cheapest mixture whose (1 - conf) quantile of the
stream-level ratio (picks so far + remaining tasks at the candidate mixture, over joint samples = a task bootstrap of
half A combined with Beta posteriors of its own pulls) clears tau. Test: changing every outcome from position t0 on
leaves decisions up to t0 identical, and nothing of task t is read before choosing for it.

L3 verdict. NO CONTROLLER BEATS THE HONEST OFFLINE MIXTURE AT AN EQUAL VIOLATION RATE. On tiers it ties within 0.01. On
models it is worse by 0.04-0.22 of the bill at tau = 0.95 and by 0-0.06 at tau = 0.90. What it gives is a risk knob,
and that knob is only roughly calibrated. Declared conf 0.90 / 0.95 / 0.99 gives end-of-stream violations of
11-14 % / 9.5-12.5 % / 5.5-6.5 % on tiers and 7.5-9.5 % / 5-9 % / 2.5-4.5 % on models (under-covers by about 2x at
high conf). Violation at any point after a burn-in of 50 tasks is high for every policy that saves anything
(25-55 % for the controller), because the running ratio over few tasks is noisy. Compared with stage 2's threshold
bandit (42 % violation at about 13 % saving), both the offline mixture with a +0.01 to +0.02 margin and lcb 0.9 hold
the target with a stated risk. Caveat in the baseline's favour: the offline curve's margin -> violation mapping was
read on half B (a frontier). A fully out-of-sample offline policy would have to pick d by resampling half A, which
was not run, and that would cost it some of its advantage.

======================================================================================================
L2 - ROUTING BY KIND OF WORK (criterion 3'; make workload; stage4_workload.py; figure stage4_workload.png)
======================================================================================================
Data: TwinRouterBench static bank, 970 steps / 520 trajectories / 5 workloads. Features come only from each
trajectory's FIRST request (the lowest step_index): system text, `functions` (names, count), the first user message
(shape, and its words in one variant), the number of messages. Test: mutating all labels, metadata, later steps and
non-first-user messages leaves the features unchanged. No client field exists in the bank. CV: StratifiedGroupKFold(5)
over trajectories, grouped by source document (270 groups: mtRAG conversation, QMSum meeting, BFCL function set).
L2a. TRIVIALITY, stated plainly. swebench, mtrag and qmsum each have ONE system prompt; bfcl 2; pinchbench 12 (one
  per task, all sharing the OpenClaw preamble). Only bfcl sends tools (2-37 functions). Accuracy (bootstrap
  interval over trajectories):
    full (system + tools + shape)   1.000 [1.000, 1.000]
    masked (no system prompt)       1.000 [1.000, 1.000]
    masked + first-user words       1.000
    shape only (no system, no tools) 0.996 [0.990, 1.000]; recall 1.0 everywhere except bfcl 0.985 (1 -> mtrag, 1 -> qmsum)
  The "classifier" is a lookup of the scaffold, and even message shape alone recognises the five workloads. The
  contribution is the per-workload policy, not the classifier.
L2b. Policy = the training fold's most frequent gold tier for the predicted workload (swebench -> high, every other
  workload -> low). Benchmark v2 combined score [95 %, 1000 trajectory bootstraps stratified by workload]:
    always-low 63.6 [61.0, 66.3]; always-high 54.4; oracle 90.7 [89.9, 91.7]; stage 3 step model (LOTO) 70.6
    true-workload prior, same folds   81.1 [79.2, 83.1] (cost-savings 56.7, trajectory pass 93.1, raw saved 77.1 %)
    classifier, every feature set     81.1 [79.2, 83.1] - identical tiers on 100 % of steps (shape only too)
L2c. Unseen workload (leave-one-workload-out). The classifier must name a known workload; every held-out workload
  ends up with the "low" tier (SWE goes 39/40 to mtrag, so coding sessions are served low and every SWE trajectory
  fails):
    no fallback                61.2 [58.4, 64.0] (full) / 61.5 [58.9, 64.3] (masked); trajectory pass 58.5 %
    novelty -> high (safe)     54.4 (full: an unseen system prompt is flagged in 100 % of unseen sessions, 0 % false
                               flags) / 56.2 (masked: kNN distance flags 100 % of four unseen workloads and 57 % of
                               qmsum, 1.0-1.2 % false flags on known ones); trajectory pass 99.3-100 %
    novelty -> mid             51.2 / 52.1
  Benchmark metric vs quality: on the metric, always-low (63.6) beats every fallback because the metric rewards cheap
  tiers and exact match. On quality, "unknown scaffold -> safe tier" keeps 99-100 % of trajectories passing at about
  0-5 % saving. A router should do the latter and say what it costs: an unseen workload is served at full price
  until enough outcomes accumulate to set its tier (an L1/L3 job). Stage 3's LOWO step model scored 57.6.
L2d. Mapping to the production router (docs/autoroute.md; observe signals are history-only by default):
    HAS per request: client_model (body model), client_has_thinking, client_tool_names (tool name CSV = the tool
      list and its count), bg_signal (client model matches background patterns), hk_text_signal (housekeeping text),
      the harness's x-octo-agent-role (orchestrator / sub) and x-octo-tier-hint (+ x-octo-tier-policy), the
      sub-agent session key (hash of the first user message), the request body (system prompt, messages: their
      count and shape are computable).
    LACKS: a stored system-prompt fingerprint / scaffold id per session (the system text is not a logged observe
      signal), the first user message's shape features (length, code blocks, paths) as a logged signal, a client id
      beyond the model string (no User-Agent / client-name column in the documented signals), a workload label, and
      a per-session outcome to learn the per-workload tier from.
    So: log a hash of the normalised system prompt and of the sorted tool-name list per session. That already
    reproduces L2's classifier as a lookup, and the per-workload tier is the learned part.

SYNTHESIS (one page)
======================================================================================================
L1  Headline: at V = $1 per solved task a cost-aware Thompson bandit over 33 concrete models earns 0.550 [0.469, 0.602]
    reward per task against the list-price ladder's 0.310 (best rung in hindsight) and the hindsight-best model's
    0.685. Strongest baseline: a ladder from a leaderboard measured on a held-out half: 0.686. Clears the
    list-price ladder: YES at every V except quality-only (0.665 vs 0.676). Clears the leaderboard: NO. It never gets
    within 0.02 per task of the best fixed model in 500 tasks. Adapts: adopts a new best model in a median of 35-50
    tasks and drops a degraded one in 16-55 (forgetting halves that and costs +35-90 % regret when nothing changes).
    Thesis sentence: "Learning the ladder online from bandit feedback beats a ladder fixed by list price by a wide
    margin, but on stationary traffic it does not beat a ladder read off a leaderboard measured on the same kind of
    tasks; its value is re-learning when models are added or change, which it does within tens of tasks."
L2  Headline: the workload is recognised from the first request with accuracy 1.000 [1.000, 1.000], even with the
    system prompt masked (0.996 from message shape alone), and the per-workload policy scores 81.1 [79.2, 83.1]
    on TwinRouterBench's v2 metric. Strongest baseline: the same policy given the true workload, 81.1. Equal, not
    better; it beats always-low 63.6 and stage 3's step model 70.6. Unseen workload: 61.2-61.5 without fallback (below
    always-low), 54-56 with the safe fallback (99-100 % trajectories pass).
    Thesis sentence: "On this benchmark each kind of work arrives with its own scaffold, so recognising it is a
    lookup, not a learning problem; the gain over a fixed tier (81.1 vs 63.6) comes from setting the tier per kind of
    work, and an unrecognised kind must fall back to a safe tier because nothing transfers between kinds."
L3  Headline: at tau = 0.95 on tiers the LCB controller (conf 0.9) keeps quality 0.962 [0.937, 0.978] of always-high
    at a saving of 10.7 % [7.5, 15.9], violating at the end in 11 % of streams. Strongest baseline: the offline
    mixture tuned on a held-out half, made continuous by randomising margins: 10.6 % at the same violation rate.
    Clears it: NO. Ties on tiers; 0-22 points of the bill worse on models. The declared confidence under-covers by
    about 2x.
    Thesis sentence: "A declared quality target can be held online with a stated, roughly calibrated risk, an
    improvement on stage 2's threshold bandit (42 % violation); but it is not cheaper than an offline mixture tuned
    on held-out data with a small safety margin, so the online controller's value is the explicit risk parameter
    and robustness to drift, not savings."

What a production integration needs (to feed L1 and L3 from the router's own traffic):
  Per session: session key; scaffold fingerprint (hash of the system prompt + sorted tool names: L2); served model(s)
  per turn and the share of the session's tokens per model; cost (cost_micros, with cost_source); tier and trigger;
  the router's decision probabilities (to allow off-policy evaluation later); an OUTCOME signal.
  Candidate outcome signals without ground-truth tests:
    - tests passed in tool output: the router already parses cargo / pytest / unittest summaries into
      session_outcomes; use "last test run green" and "red -> green during the session";
    - the person's accept / rewind / discard in the harness (v7 changes and approvals: accepted change sets,
      reverted changes);
    - a follow-up correction: the next user turn says "wrong / doesn't work / revert", or the same task is re-asked;
    - stall / escalation triggers already logged (stall:*, retry, budget_cap) as negative signals;
    - session abandoned without an accepted change.
  All of these are noisy proxies. L1 / L3 must treat them as a weaker label (noise rate unknown, not measured here).
Riskiest assumption of each part:
  L1: that the outcome proxy is unbiased across models. If one model's sessions produce more test output, or are
      accepted more readily, the bandit learns the proxy, not quality. Also that traffic is stationary enough for
      500-1 000 sessions per decision, which is the horizon at which it still lags a leaderboard.
  L2: that real workloads come with distinct scaffolds as on the benchmark. Inside one scaffold (a coding agent
      doing many kinds of work) L2 has nothing to recognise, and stage 3 found per-step routing does not pay there.
  L3: that offline (or early) data are exchangeable with the stream. Its coverage is about 2x off even under
      exchangeability; with drift (not tested here) the violation rate is unknown.

======================================================================================================
LEFT / NOT DONE (time box ~100 min)
======================================================================================================
- L1: "best fixed triple in hindsight" (criterion 2' names it) not computed; only the best fixed model. The tier view
  for the constrained objective and for ts_band was not reported. Sensitivity to T0, sigma_c, n0 was not run (all
  fixed up front). The created_at order has a single order, so its intervals reflect only the policies' randomness.
- L1/L3: drift that a leaderboard does not see (a model better on the router's own workload than on SWE-bench) cannot
  be built from this data; the "new model" and "degrade" scenarios are synthetic edits of the matrix.
- L3: an offline policy whose margin d is chosen out of sample (by bootstrap on half A), which would be the fully
  honest offline baseline; the controller on L1's objective (i). The any-point violation uses the expected
  (tiers) / realized (models) running ratio, which is noisy over the first tasks.
- L2: no client field in the bank; production signals were mapped from the docs, not measured on router traffic.
  A thresholded (q) per-workload policy and intervals on its difference from the true-workload prior were not run
  (the tiers were identical on 100 % of steps, so the difference is exactly 0).
- Nothing was run against the router or the harness; no API calls; no git writes.
