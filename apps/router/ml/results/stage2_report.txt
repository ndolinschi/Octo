STAGE 2 REPORT - where is the signal a router could use, if not in the task's text?
Date 2026-11-13. Location: apps/router/ml/. Every number below is in results/stage2_*.json.
Data: stage 1's core, unchanged (39 mini-SWE-agent submissions x 500 SWE-bench Verified tasks, scheme A headline,
tiers low 12 / mid 11 / high 16 submissions). Seeds: config.SEED + offsets. Tests: 18 pass (14 stage 1 + 4 new).
Curve area ("AUC") = stage 1's metric (upper hull of operating points, averaged over cost from always-low to
always-high). "Mixture" = the hull of fixed tiers = the per-tier prior. Intervals are 95 %.

======================================================================================================
A. IS THERE ANYTHING TO PREDICT? (make ceiling; stage2_ceiling.json; figures/stage2_ceiling.png)
======================================================================================================
Method: 200 random splits of each tier's submissions into two disjoint halves (independently per tier);
r = correlation across tasks of the halves' values; reliability = Spearman-Brown 2r/(1+r). Intervals: over splits
combined with a task bootstrap.

Reliability, scheme A (B and C are within +-0.05 and lead to the same reading):
  soft label low   0.90 [0.86, 0.93]     mid 0.92 [0.88, 0.94]     high 0.965 [0.95, 0.975]
  advantage high-low 0.54 [0.38, 0.68]
  advantage mid-low  0.11 [-0.26, 0.31]   (B: 0.32 [0.01, 0.48]; C: 0.06)
  advantage high-mid 0.18 [-0.14, 0.41]
Mean advantages: high-low +0.198 (negative on 7.8 % of tasks), mid-low +0.124, high-mid +0.074.

Honest ceiling: Lagrangian oracle built on a fraction f of each tier's submissions and scored on the disjoint rest
(curve area minus the mixture's on the scoring part). Raw build labels under-use the signal (noisy decisions), so
an empirical-Bayes shrunk version (beta-binomial, fitted on the build part only) is reported too.
                      in-sample oracle   cross-fit raw              cross-fit EB
  A, f=0.5            +0.097             +0.008 [-0.035, +0.031]    +0.014 [-0.029, +0.039]
  A, f=0.25 / 0.75    +0.086 / +0.113    +0.006 / +0.007            +0.017 [-0.008,+0.034] / +0.010 [-0.040,+0.047]
  B, f=0.5            +0.086             +0.007 [-0.028, +0.024]    +0.014 [-0.012, +0.030]
  C, f=0.5            +0.090             -0.003 [-0.049, +0.020]    +0.003 [-0.043, +0.027]
  (stage 1, full data, in-sample: A +0.080, B +0.062, C +0.071)
Cost saved at 95 % of always-high, EB cross-fit minus mixture (paired), A f=0.5: +8.4 pp [-18, +21].

Meaning, said plainly:
- The tier labels themselves are reliable; what is NOT reliable is which tier is better on a given task. Only the
  low-vs-high gap has a real task-level component (about half of its variance); the gaps that involve mid are
  indistinguishable from noise with 10-19 runs per tier.
- About 85 % of the oracle's +0.080 is fitting run-to-run noise. A router that knew each task's held-out
  label perfectly from an independent set of runs would gain about +0.01 curve area over the per-tier prior
  (scheme A: +0.014, interval includes 0; it does not grow from f=0.25 to 0.75). This is an upper bound for ANY
  task-level predictor on this data, text or otherwise. Stage 1's M1 = prior is therefore not mainly a failure of
  the text features: the room it had to fill was ~0.01, not 0.08. The thesis should say this. (Caveat: the
  cross-fit oracle uses noisy estimates of p, so the true-p ceiling lies between the cross-fit +0.014 and the
  in-sample +0.08; the flat trend over f suggests it is near the low end.)

======================================================================================================
B. SIGNAL AFTER THE CHEAP MODEL HAS WORKED (cascade)
======================================================================================================
B1. Post-hoc run features (make cascade; stage2_cascade.json; figures/stage2_cascade.png)
per_instance_details.json holds exactly three fields per instance: api_calls, cost, resolved (checked over all
39 core submissions). Exit status / submitted / step-limit are NOT there (only in trajectories, B2). Features:
log calls, log cost, log cost per call, limit flag (calls >= 250 or cost >= $2.95 = mini-SWE-agent's defaults).
Detector: LR, leave-one-repository-out; label "run did not resolve". AUROC reported WITHIN each model (pooling
rows across models inflates it with base-rate differences: 0.79 pooled vs 0.705 within).
  low tier (12 subs, fail 51 %):  within-model AUROC 0.705 [0.684, 0.728]; per-model LR 0.71; unfitted
                                  "more calls = failed" 0.689 [0.676, 0.711]. Brier skill vs per-model prior +0.12.
                                  Per model 0.65 (deepseek-v3.2-reasoner) to 0.79 (Llama-4-Maverick).
  mid tier (10 subs, fail 40 %):  0.652 [0.62, 0.69] pooled, 0.677 per-model.
So a finished run's length/cost carries a moderate failure signal (AUROC ~0.70).

Cascade on the matrix (run a cheap submission to the end, escalate when the detector fires; escalated outcome =
the dearer tier's soft label; cost = c_cheap + c_dearer when escalated; averaged over cheap submissions; same
fixed-tier baselines as stage 1). Scheme A, low -> high, 200 repository-cluster bootstraps:
                                              AUC      minus mixture                cost saved @95 %
  mixture of fixed tiers (stage 1 baseline)   0.594    -                            13.8 %
  run features only (ranks within model)      0.590    -0.003 [-0.011, +0.004]      11.8 %
  model prior only (no run features)          0.619    +0.025 [+0.020, +0.032]      25.6 %
  run features + model prior                  0.612    +0.019 [+0.012, +0.030]      20.2 %
  perfect detector (knows if low resolved)    0.622    +0.027 [+0.016, +0.037]      26.3 %
  features+prior minus prior only: -0.006 [-0.010, -0.002]. Features only minus random escalation: +0.003
  [+0.002, +0.005]. At the escalation rate equal to the failure rate, run features capture 10 % of the perfect
  detector's quality gain over random escalation.
  low -> mid: same picture (features only -0.003; prior only +0.026; perfect +0.037).
  mid -> high: nothing beats the mixture, not even the perfect detector (-0.004): paying mid then high costs more
  than high alone.
  Schemes B and C: no cascade variant beats the mixture except low->mid with the perfect detector (+0.02).
Reading: (1) the run-level detector beats random escalation but NOT the mixture of fixed tiers; the economics of
a post-hoc cascade (the cheap run is paid in full) leave room only for a near-perfect detector, and even that
gains only +0.027 (A). (2) The apparent gain of the pooled detector comes from its per-model intercept: it
escalates weak cheap models (qwen2.5-coder-32b 9 % solved, Llama-4-Maverick 21 %) wholesale. That is
model selection inside the cheap tier, not task routing; "model prior only" does it better. Practical
consequence for the router: choose the cheap model well (the low tier's mean hides a 9 %-76 % spread).

B2. Trajectories (make trajectories; stage2_trajectories.json; figures/stage2_trajectories.png)
Obtained: full mini-SWE-agent trajectories are public, anonymous HTTPS on the S3 bucket named in each
submission's metadata (https://swe-bench-submissions.s3.amazonaws.com/bash-only/<sub>/trajs/<id>/<id>.traj.json;
ETag/LastModified kept in data/trajs/*/_manifest.json; no revision exists). Downloaded 9 of the 12 low-tier
(scheme A) submissions x 500 tasks = 4 500 runs, 1.55 GB (skipped for size: Llama-4-Maverick 3.6 GB, minimax-m2,
deepseek-v3.2-reasoner). Formats mini-swe-agent-1 (text + bash block) and 1.1 (tool calls / responses API) are
normalised to steps; steps match api_calls (median |diff| 0-1). Per-step cost is recorded only in the three 2.x
runs; the others use cost x K / steps (on the 2.x runs the first 10 steps cost 0.64x [0.16, 1.31] of that linear
share, so the linear rule over-charges early stops; this penalises the early cascade slightly).
Early features at K (first K steps only + "run ended by K"): tool errors, format errors, repeated commands, files
seen, view/edit/test counts, last test outcome, script runs, output sizes, tracebacks, thought length, negative/
positive words, submitted, steps since last edit. Test: changing anything after step K leaves them unchanged.
Within-model AUROC for final failure (LORO, pooled LR, 200 repository bootstraps):
  K=5   0.542 [0.512, 0.557]     K=10  0.608 [0.589, 0.626]     K=20  0.642 [0.629, 0.650]
  (only "ended by K" + step count: 0.44 / 0.49 / 0.56)
  post-hoc api_calls+cost 0.700 [0.684, 0.720]; post-hoc full trajectory + exit status + calls + cost 0.716
  [0.704, 0.738]. Runs ended by K: 1.8 % / 11.7 % / 34.7 %. Strongest single features at K=10: number of view
  commands (0.60), output size (0.57); test outcomes and the agent's words ~0.5.
Early cascade (stop at K when the detector fires, run high; scheme A; cheap point = these 9 submissions):
  mixture 0.592; features only: K5 +0.003 [-0.002, +0.009], K10 +0.000 [-0.005, +0.007], K20 -0.003 [-0.007,
  +0.001]. Model prior only, stopping at K5: +0.046 [+0.041, +0.049] (again: dropping weak cheap models early);
  features + prior at K5 +0.042 (below prior only). Perfect stop at K5: 0.660 (+0.068) - the room an early
  detector would have if it existed. Random stop at the same K: 0.590.
Reading: early trajectory signal exists and grows with K (0.54 -> 0.64) but stays below the post-hoc signal
and is far too weak to make an early cascade beat the fixed-tier mixture once the model-level effect is removed.
Not done: TF-IDF/embeddings of the agent's text, learned sequence models (SWE-Router uses a 7B value head; not
feasible on 4 CPUs), per-step-cost correction of the linear rule for v1 runs, the other 3 low submissions.

B3. TwinRouterBench step-level check (make steps; stage2_steps.json)
336 SWE steps from 40 Verified tasks; target_tier collapsed by scheme A prices (low+mid -> low 127, mid_high ->
mid 41, high 168); labels vary inside 98 % of tasks. Leave-one-TASK-out, multinomial LR; 1000 task bootstraps.
  majority: acc 0.50, balanced acc 0.33, log loss 0.977
  step_index only: acc 0.52, bal 0.355, log loss 0.977 (no gain)
  step-time numeric features (index, prefix length/chars, tool errors, tests, edits, last command kind):
     acc 0.66 [0.60, 0.71], bal 0.50, log loss 0.868; vs majority -0.108 [-0.179, -0.029]
  + TF-IDF of the last message: acc 0.68 [0.64, 0.72], bal 0.51, log loss vs majority -0.119 [-0.195, -0.035]
  It under-tiers 12-14 % of steps (predicts cheaper than needed), which in TwinRouterBench's definition can break
  the trajectory. Small (40 tasks, one benchmark build marked "not ground_truth_ready"); it shows that the session
  prefix carries step-level information that the task statement does not, nothing more.

======================================================================================================
C. ONLINE ADAPTATION (make bandit; stage2_bandit.json; figures/stage2_bandit.png)
======================================================================================================
Setup: 200 streams; repositories in random order, tasks in created_at order; the policy sees only the chosen
tier's 0/1 outcome (drawn from the soft label, common random numbers; a test flips every unobserved outcome and
checks the choices do not change). Price list known (mean cost per tier on the other repositories). Evaluation
on expected values. Regret over 500 tasks against (i) best fixed tier per repository in hindsight, (ii) the
global best fixed tier. EB prior strengths fitted from between-repository variance: n0 = 68 / 38 / 26 (strong
prior: little is repository-specific, consistent with stage 1's 6-8 %).
Objective quality - lambda*cost, lambda in {0, .25, .4, .5, .6, .75, 1, 2} per $:
- Away from the break-even (lambda <= 0.4: always-high is best; lambda >= 0.75: always-low is best) every adaptive
  policy loses to the fixed best tier: e.g. lambda=0 regret vs global best: TS-EB 10.1 [4.8, 18.8], UCB-EB 14.0,
  TS flat per repo 25.7, UCB flat 36.3 (fixed high 0). With lambda=2, TS-EB matches it (0.5 [-0.5, 2.2]).
- Near break-even (lambda 0.5-0.6) the per-repository best tier differs from the global one; the maximum that
  per-repository adaptation could gain is the regret of the global best tier vs per-repository best: 6.9 (0.5)
  and 8.4 (0.6) over 500 tasks, i.e. <= 0.017 per task. Bandits do not collect it: regret vs per-repo best 10-13
  (all worse than fixed mid), regret vs global best +3.2 to +5.2 (intervals touch 0 for TS/UCB-EB).
  They do beat the leave-one-repository-out global prior at lambda=0.6 (7.1), whose offline choice is unstable.
- Tasks until within 0.01 per task of the repository's best tier: never reached for most policies (regret per
  task at positions 50+ in a repository is still 0.01-0.04); the margin metric is uninformative here.
Constrained objective (min cost s.t. quality >= 95 % of always-high):
  offline mixture (other repos):  quality 0.951 [0.943, 0.960] of high, cost 0.866, meets 95 % in 61 % of streams
  threshold bandit (EB + Robbins-Monro tau): 0.953 [0.915, 0.984], cost 0.871 [0.770, 0.963], meets in 58 %
  Lagrangian TS (EB, dual ascent):  0.902 [0.863, 0.936], cost 0.751 - violates the constraint in every stream
  reference: stage 1 mixture saves 13.8 % at 95 %; in-sample oracle 50.5 % (mostly noise, part A).
Reading: online adaptation over three tiers per repository gains nothing measurable on this data; the threshold
bandit reproduces the offline mixture, Thompson/UCB pay exploration for a repository effect that is ~1-2 points
at most. This is what part A predicted.

======================================================================================================
D. SYNTHESIS
======================================================================================================
What a router can use, ranked by measured gain in curve area over the fixed-tier mixture (scheme A):
 1. Choice of the cheap model (model-level, not task-level): escalating/dropping weak low-tier models wholesale
    +0.025 [+0.020, +0.032] post-hoc, +0.046 [+0.041, +0.049] if they are stopped at step 5. Not routing - it says
    the tier should be one good cheap model, not an average of 12.
 2. Task-level oracle knowledge from independent runs (ceiling for any task-level predictor): +0.014 [-0.029,
    +0.039] - not significantly above zero.
 3. Step-level session state (TwinRouterBench): beats majority and step-index in log loss (-0.11 [-0.18, -0.03]),
    small and on 40 tasks; no cost-quality number.
 4. Post-hoc run length/cost of a cheap run: AUROC 0.70 within model, but as a cascade -0.003 [-0.011, +0.004];
    early (K=5/10/20) trajectory features: AUROC 0.54/0.61/0.64, cascade +0.003/0.000/-0.003 (all n.s.).
 5. Per-repository online adaptation: <= 0.017 per task available at break-even lambda, not captured (bandits
    lose 3-5 reward units vs the global best tier over 500 tasks).
What it cannot use: the task's text (stage 1), the repository identity (6-8 % of variance, part C), mid-tier
advantages (reliability ~0.1-0.2, part A), a post-hoc or early cascade at these price ratios (part B).
For the thesis: the claim "a learned router predicts which tier solves a task" is not supported by public
SWE-bench data; the defensible claims are (a) the measured noise ceiling (most oracle headroom is run-to-run
noise), (b) the negative results with intervals for text, cascade and bandit, (c) the model-selection effect.
"Adaptive" can be kept only as "adapts the operating point (threshold/mixture) online to hit a quality target",
which the threshold bandit does as well as the offline mixture, not as "learns per project which tier to use".
For the router: log per session the cheap model, steps, tool errors, test runs, and the final outcome (the
harness's solved/not-solved, which history lacks today) - outcome variance per model is the decision that pays;
learn the cheap model's identity/quality per task family, not the tier from the prompt.
Revised model (not built): the router keeps a fixed per-tier policy whose operating point (mixture or threshold)
is adapted online to a declared quality target, and chooses which concrete model fills the cheap tier from
logged per-model success rates. A step-level escalation detector over the session prefix is kept as a research
track, to be adopted only if it beats the per-tier mixture on the router's own logged sessions.
